## What this is

Sea Snake — an iOS Snake game, SwiftUI + SpriteKit. Xcode project at `SnakeGame.xcodeproj`, source under `SnakeGame/`.

## Commands

The Xcode project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml` — it is not the source of truth. **Whenever you add, remove, move, or rename a `.swift` file (or anything under `SnakeGame/`), regenerate the project before building:**

```bash
xcodegen generate
```

Build for the simulator (swap the destination for whatever's booted; `xcrun simctl list devices` to see options):

```bash
xcodebuild -project SnakeGame.xcodeproj -scheme SnakeGame -destination 'id=<SIMULATOR_UDID>' build
```

or, without needing a booted device first:

```bash
xcodebuild -project SnakeGame.xcodeproj -scheme SnakeGame -destination 'generic/platform=iOS Simulator' build
```

There is no test target yet.

## Architecture

### SwiftUI shell vs. SpriteKit game

The app is split cleanly at the framework boundary: SwiftUI owns navigation and chrome, SpriteKit owns the game itself.

- `SnakeGameApp` → `RootView` → either `StartView` or `ContentView`, switched on `@State private var isPlaying`. Switching is a hard swap (`if/else`, not a `NavigationStack`), so a fresh `ContentView` — and so a fresh `GameScene` and `GameSessionState` — is created every time Play is tapped. Nothing about a previous run persists across a re-entry to the game.
- `ContentView` hosts a single `SpriteView(scene:)`. From there down, SpriteKit's retained-mode scene graph takes over: nodes are mutated in place, not redrawn from scratch each frame.
- Game-over is *not* handled inside the scene. `GameScene` exposes a plain `onGameOver: (() -> Void)?` closure; `ContentView` wires that into `@StateObject private var session: GameSessionState` (`@Published var isGameOver`), which drives a SwiftUI `GameOverOverlay` shown over the `SpriteView`. Restart and "go home" are both SwiftUI-side actions (`scene.startNewGame()` / a closure back up to `RootView`) — swiping never restarts the game.

### Mode selection flows downward, ahead of geometry

`GameMode` (`.freePlay` / `.levels`, `CaseIterable` so new modes don't need toggle-logic changes) is chosen on `StartView` and owned by `RootView`. It has to reach `GameScene` *before* `didMove(to:)` runs, because the grid's `columns`/`rows` (and therefore `cellSize`/`origin`) depend on the mode — free-play is a fixed 16×24 centered square grid with a border; levels mode is 16×30, no border, sized from whichever level a run starts on. That's why `GameScene` takes `mode` as an init parameter rather than being constructed bare and configured after the fact.

### GameManager orchestrates; each grid entity owns its own state + rendering

`GameManager` is the only thing that knows about scoring, collisions between different entity types, and game-over. It does *not* own rendering directly — `Snake`, `Food`, `PowerUp`, `Bomb`, and `Walls` each manage their own `SKNode`(s) and expose `addToScene(_:)`/`removeFromScene()`. This split matters for two reasons:

1. **Collision ordering encodes what can protect you.** `Snake.advance(...)` only checks self-collision (it doesn't know food, bombs, walls, or power-ups exist). Everything else — food-eaten, wall contact, bomb contact, power-up pickup — is resolved by `GameManager` *after* `advance()` commits the move, by comparing `snake.head` against each entity's position. The order those checks run in is deliberate: power-up pickup resolves before bomb-collision in the same tick, so grabbing bomb-eater and hitting a bomb in one move grants immunity for that same collision rather than ending the run a beat early. Wall contact has no such interplay (nothing grants wall immunity) and is checked unconditionally.
2. **Rendering strategy differs by how often a thing changes.** `Snake` reuses/repositions its segment nodes every tick rather than destroying and rebuilding them (`syncNodes()`) — worth preserving as things get more visually complex. `Food`/`PowerUp`/`Bomb`/`Walls` are simpler since they don't move once placed (or, for `Food`/`PowerUp`, just get replaced wholesale on relocate/respawn).

### Grid coordinate convention

`GridPoint(x: 0, y: 0)` is the **bottom-left** cell. `y` increases upward, matching `Direction.up.vector == (0, 1)` and SpriteKit's own y-up coordinate system — `GridGeometry.position(for:cellSize:origin:)` is the single place grid coordinates become screen points, and everything (`Snake`, `Food`, `PowerUp`, `Bomb`, `Walls`) routes through it rather than computing its own. `Level.walls` has to flip its ASCII map's row order to honor this (the map's first string is visually the top row, i.e. the *highest* `y`).

### Game loop is tick-based, not per-frame

`GameScene.update(_:)` runs every frame (~60/sec) and forwards to `GameManager.tick(currentTime:)`, but grid movement only advances once `timeSinceLastMove` accumulates past `moveInterval` — the standard "decouple game logic from frame rate" pattern. `moveInterval` is driven purely by fruit eaten (it has no relationship to snake length; confirmed independent since `tail-cutter` shrinks the snake without touching it). Timed effects like bomb-eater's ~5-second immunity are tracked separately in real elapsed time (`bombEaterTimeRemaining -= delta`, decremented every frame) rather than in grid ticks, so they don't speed up or slow down with the snake.

### Levels

`Level` (in `Level.swift`) defines a layout as an ASCII grid (`-` empty, anything else a wall) plus `pointsToAdvance`, mirroring the shape of the original Python prototype's `LEVELS` list. `Level.all` is the fixed roster of three; all three currently share one grid size since `cellSize` is computed once per run and can't change without rebuilding the scene. `GameManager` tracks level advancement via a *separate* `levelProgress` counter, not the run's total `score` — thresholds compare against `levelProgress`, which resets to 0 on every advance, specifically so cycling back to level 1 after the last level doesn't instantly re-trigger every threshold against an already-high total score. On advance, walls/food/bombs/power-up are swapped/cleared, but the snake and total score carry over.
